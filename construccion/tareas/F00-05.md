**Modalidad:** control. **Dependencias:** F00-04.
**Gate:** PRESENT (no significa PASS).

- `AGENTS.md`
- `docs/CONTEXTO-CANONICO.md`

## Pasos específicos
1. Control-plane escribe y revisa el gate del SIGUIENTE incremento antes de crear su worktree; ningún worker escribe tests/acceptance.
2. Registrar todos los gates como authored o missing con evidencia actual, no PASS; congelar hashes de los disponibles.
3. Probar el primer gate sobre candidato vacío y candidato defectuoso; commit de control antes de prepare/run. Repetir este protocolo antes de CADA tarea posterior.

## Oráculos obligatorios para el gate
- F01-01 tiene gate real y negativo de scaffold ausente.
- El registro no puede decir authored para un archivo ausente.
- Existencia del gate no cuenta como aceptación del producto ni 55 tareas ejecutadas.

## Preparar la prueba ANTES del worker
1. Controlador escribe el gate siguiente a partir de los oráculos de arriba. Si requiere DB/browser, seguir 04-PRUEBAS-Y-LOOP.md; no sustituirlo por un JSON que diga passed.
2. Ejecutar contra implementación ausente y contra el defecto específico (nulo→cero, duplicado, fuga, según tarea). Registrar fallo por la aserción correcta; un error de setup NO mata un mutante.
3. Revisar gate fuera del candidato y hacer commit. Refrescar registro de gates y guía al agregar pruebas, antes de prepare, nunca durante una verificación.

## Comandos del ciclo
```bash
cd ~/vexa
python3 scripts/guide.py audit
python3 scripts/guide.py packet --task F00-05
python3 orchestration/runner.py prepare --task F00-05 --max-minutes 1
# Editar sólo el worktree impreso, sin commit; guardar su ruta en CANDIDATE.
VEXA_CANDIDATE="$CANDIDATE" node --test tests/acceptance/F00-05.test.mjs
python3 orchestration/runner.py verify --task F00-05 --max-minutes 5 --approval-note "REFERENCIA A LA DECISIÓN REAL DEL OPERADOR"
# Revisión independiente de diff, controles y log; NO aceptar por autoafirmación.
# Si se rechaza: STOP + reject --task F00-05 --approval-note "referencia real"; ver capítulo 01.
python3 orchestration/runner.py accept --task F00-05 --max-minutes 5
```
Estos comandos fallan cerrados si faltan gate/dependencias/permiso; no son evidencia de ejecución. No pegar la nota de ejemplo como aprobación. La modalidad external requiere actos fuera del loop; prepare sólo abre un candidato local.

## Recuperación específica
Si falta gate futuro, guía indica primero su contrato y casos; no arrancar worker para que lo invente.

`task_id, baseline_sha, candidate_sha, fixture_hash, command, exit_code, expected, observed, artifacts, reviewer, pending`. Las pruebas/grafo no las edita el candidato. Dos fallos agotan intento; guardar reproducción y pasar a recuperación supervisada, no editar status=accepted.
