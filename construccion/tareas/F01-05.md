## Pasos específicos
1. Crear jobs separados: controlador/kernel, typecheck/lint/build, integración Supabase local, E2E; checkout del SHA del candidato.
2. npm ci desde lock; credenciales sólo de DB efímera, nunca prod ni fork público privilegiado.
3. Invocar gates protegidos del baseline sobre VEXA_CANDIDATE; proteger workflow y tests fuera de allowlist ordinaria.
4. En local demostrar fallo con build roto y con fuga RLS; CI remoto requiere permiso de repositorio.

## Oráculos obligatorios para el gate
- Un tsc error, migración rota o oráculo de B hacen job rojo.
- No continue-on-error/skip para tests críticos.
- CI remoto verde sólo con run_id y SHA efectivos; YAML válido no es una corrida.

## Preparar la prueba ANTES del worker
1. Controlador escribe el gate siguiente a partir de los oráculos de arriba. Si requiere DB/browser, seguir 04-PRUEBAS-Y-LOOP.md; no sustituirlo por un JSON que diga passed.
2. Ejecutar contra implementación ausente y contra el defecto específico (nulo→cero, duplicado, fuga, según tarea). Registrar fallo por la aserción correcta; un error de setup NO mata un mutante.
3. Revisar gate fuera del candidato y hacer commit. Refrescar registro de gates y guía al agregar pruebas, antes de prepare, nunca durante una verificación.

## Comandos del ciclo
```bash
cd ~/vexa
python3 scripts/guide.py audit
python3 scripts/guide.py packet --task F01-05
python3 orchestration/runner.py prepare --task F01-05 --max-minutes 1
# Editar sólo el worktree impreso, sin commit; guardar su ruta en CANDIDATE.
VEXA_CANDIDATE="$CANDIDATE" node --test tests/acceptance/F01-05.test.mjs
python3 orchestration/runner.py verify --task F01-05 --max-minutes 5 --approval-note "REFERENCIA A LA DECISIÓN REAL DEL OPERADOR"
# Revisión independiente de diff, controles y log; NO aceptar por autoafirmación.
# Si se rechaza: STOP + reject --task F01-05 --approval-note "referencia real"; ver capítulo 01.
python3 orchestration/runner.py accept --task F01-05 --max-minutes 5
```
Estos comandos fallan cerrados si faltan gate/dependencias/permiso; no son evidencia de ejecución. No pegar la nota de ejemplo como aprobación. La modalidad external requiere actos fuera del loop; prepare sólo abre un candidato local.

## Recuperación específica
Revertir sólo cambio de CI en rama si rompe bootstrap; no bajar umbrales ni retirar jobs para aceptar.

## Cierre obligatorio
`task_id, baseline_sha, candidate_sha, fixture_hash, command, exit_code, expected, observed, artifacts, reviewer, pending`. Las pruebas/grafo no las edita el candidato. Dos fallos agotan intento; guardar reproducción y pasar a recuperación supervisada, no editar status=accepted. Build/instalación de dependencias se hacen en copia temporal para no mutar el candidato durante el gate.
