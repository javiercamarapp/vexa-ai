# Diagnóstico de planificación y ejecución SQL

Workflow manual `capacity-server-profile.yml`, job `capacity-server-profile`, runner estándar ARM. Requiere una correlación UUID y checkouts limpios del mismo SHA en `main`. Ejecuta un único10K sintético del producto adoptado, con consumidor1, bloques100 y plazo900000ms por trabajo. No propone una optimización ni acredita50K,150K, capacidad comercial, producción o aceptación.

El controlador reutiliza bootstrap, proceso y limpieza existentes. Adapta copias efímeras del ejecutor y worker mediante sustituciones únicas comprobadas: envuelve `consume` con instantáneas y `query` con instrumentación. Los archivos canónicos de producto, ejecutor, worker, generador y harness permanecen intactos. Conserva contadores SQL/API, comprobación de checkpoints y deadlines del ejecutor, inventario antes/después y limpieza de cinco recursos. Presupuesto del proceso1800s; workflow40min, incluyendo bootstrap y limpieza.

La instancia PostgreSQL es exclusivamente la creada por el harness. Primero comprueba PostgreSQL17, `shared_preload_libraries` y extensión instalada `pg_stat_statements`. Si falta el módulo, la extensión o alguna columna requerida, falla y limpia; no reinicia ni cambia el harness. Activa `track_planning=on`, `track=all` y `compute_query_id=on` con configuración de esa base desechable. Nunca usa `ALTER SYSTEM`. Comprueba los valores efectivos en cada conexión instrumentada antes de sus consultas de aplicación. Un cero con seguimiento apagado no se interpreta como coste cero. Referencia de contrato: [PostgreSQL17: pg_stat_statements](https://www.postgresql.org/docs/17/pgstatstatements.html).

Las instantáneas delimitan exactamente una llamada a `consume`, después del upload/confirm y antes de consultas de verificación. Se identifican entradas por usuario, base, `toplevel` y `queryid`; se rechazan reinicios, expulsiones, disminuciones de contadores y desapariciones. Se conservan deltas separados de planes, llamadas, planificación, ejecución, buffers y WAL. Las consultas anidadas quedan en una partición separada y no se suman a las de nivel superior.

Se mapean cinco formas DML principales, cada una con9800 llamadas esperadas, y el contador de duplicados, con100. SQL público estático y hash de cliente fijan la forma. La correspondencia servidor conserva posiciones de todos los parámetros originales; sólo admite normalización de los literales enteros conocidos del contador a nuevos parámetros. Correspondencias múltiples, formas ausentes o conteos diferentes fallan. Las formas restantes se identifican por hashes, nunca por texto o valores exportados. No se exportan bindings, credenciales ni payloads.

`benchmark/report.json` conserva la evidencia del ejecutor; `benchmark/server-profile.json` contiene snapshots y deltas; `benchmark/client-profile.json` contiene perfil cliente y comprobaciones de conexiones. El recibo es `capacity-server-profile-v1`; únicamente un diagnóstico completo y limpiado emite `MEASURED_10K_SERVER_PROFILE_DIAGNOSTIC_VERIFIED`. El transporte mantiene8MiB por archivo,16MiB por bundle y2MiB comprimidos, con bloques `VEXA_CAPACITY_EVIDENCE_*`.

El seguimiento de planificación añade overhead, cuya magnitud no mide este ensayo. El residuo entre tiempos cliente y servidor no identifica por sí solo CPU, red o espera. La evidencia puede orientar un experimento posterior; no demuestra que reutilizar preparación vaya a mejorar el rendimiento. No se ejecutan modelos ni se usan datos cliente. Publicación y despacho requieren controles independientes; este archivo no los autoriza.
