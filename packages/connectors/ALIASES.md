# Alias explícitos y duraderos

`createAliasRepository({database})` en `aliases.mjs` recibe exclusivamente el límite servidor `createDatabase` de platform. No conecta un cliente service-role ni mantiene el estado en memoria. Usa la tabla `external_aliases` existente y la extensión SQL aditiva `0009_aliases.sql` sobre0001–0008; no reescribe migraciones aplicadas.

- `propose({sourceConversationId,targetConversationId})` lee identidades exactas y versión vigente bajo acción `propose`. Devuelve una propuesta, nunca escribe una aprobación. La UI debe presentar ambas fuentes, evidencia y razón para confirmación humana. Texto o email coincidentes no conceden identidad.
- `confirm({sourceConversationId,targetConversationId,expectedVersion,evidenceRef,reason,approved:true})` requiere owner vigente. `expectedVersion` empieza en0; la versión siguiente la confirma SQL mediante CAS. El actor se obtiene con `auth.uid()`, nunca de un body. Devuelve la fila de aprobación persistida.
- `undo({sourceConversationId,expectedVersion,evidenceRef,reason,approved:true})` agrega un evento `undo` que vuelve a la identidad original. Sólo puede deshacer una confirmación vigente. Para cambiar de destino se requiere deshacer y una nueva aprobación; no existe sobrescritura silenciosa.
- `resolve({conversationId})` devuelve `{conversation_id,canonical_id,version}`. `list()` devuelve grupos `{canonical_id,conversation_ids}`; el número de grupos es la población resuelta. Todas las IDs originales permanecen en DB. El resultado es una proyección de lectura del tenant completo, no una mutación de conversaciones o snapshots.
- `history({sourceConversationId})` conserva la secuencia completa incluyendo eventos heredados. Las filas legacy no reciben evidencia ni aprobador inventados. Cuando la última fila de alguna identidad aún es legacy, `list` y `resolve` fallan con `ALIAS_LEGACY_UNRESOLVED`; no producen cifras aparentemente comparables. `propose` expone `legacyUnresolved` y su versión para permitir una nueva confirmación explícita con evidencia.

SQL verifica existencia tenant-aware del origen y destino, cuenta/fuente de la conexión frente a procedencia histórica, origen externo exacto, actor owner vigente, evidencia no vacía, revisiones/identidades ambiguas, CAS, confirmaciones contradictorias y ciclos. Un bloqueo transaccional por tenant serializa cambios de aristas para evitar ciclos concurrentes. UPDATE/DELETE se rechazan mediante privilegios y trigger incluso por rutas heredadas; undo es append-only. No se borran fuentes, mensajes ni revisiones. Reutiliza `identityKey` ya integrado en ingesta, sin un segundo normalizador canónico.

Las conexiones conservan la identidad histórica: reasignar una conexión a otra cuenta no cambia la identidad de los alias existentes; esa incompatibilidad bloquea la operación/lectura. Un destino puede ser de otro proveedor dentro del mismo tenant, pero cada extremo debe coincidir exactamente con su propia conexión y cuenta. IDs iguales en cuentas diferentes no se fusionan automáticamente.

Las pruebas unitarias sólo acreditan validación de entrada. El gate externo F03-04 debe demostrar PostgreSQL real, RLS/roles, rollback, concurrencia, proyección5→4→5 y conservación de historial. Esta propuesta no acredita integración remota, aprobación humana real ni aceptación oficial deF03-04.

Las escrituras `confirm` y `undo` requieren aislamiento PostgreSQL `READ COMMITTED`, usado por `createDatabase`. SQL rechaza cualquier otro aislamiento antes de insertar: un snapshot previo al bloqueo por tenant podría ocultar una arista concurrente y crear un ciclo. No cambiar el aislamiento de esta frontera ni convertir el rechazo en un reintento automático con evidencia distinta.
