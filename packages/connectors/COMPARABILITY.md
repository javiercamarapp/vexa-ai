# Comparación de migración

Propuesta F03-06, independiente del panel de salud F03-05. No acredita revisión independiente, aceptación oficial ni cuentas reales.

POST /api/migrations congela el dataset autorizado; GET lista cortes mediante paginación por fecha e ID; GET /api/migrations/compare compara dos IDs explícitos de la misma organización. El panel /migrations permite capturar, seleccionar, comparar, actualizar y cargar cortes anteriores. Lecturas de miembros activos; captura sólo owner/analyst, Origin obligatorio y tenant derivado de sesión/SQL. Error SQL es503; nunca se sirve una lista vacía para simular disponibilidad.

El baseline usa metric_snapshots existente, publicado e inmutable. No hay otra tabla de snapshots ni nuevas migraciones. INSERT atómico/idempotente por scope/input/policy, huella de entradas y resumen, reloj SQL y referencias al método; no UPDATE de historia. Un SELECT compuesto lee filas canónicas, revisiones seleccionadas y alias en un mismo snapshot PostgreSQL. projectAliases es la proyección existente de F03-04 extraída sin cambiar sus reglas; no se duplican aprobaciones ni se fusiona por texto/email.

El alcance es explícito: ventana UTC por inicio de conversación, timezone del contrato, moneda, fuentes y canales. Los mensajes y órdenes siguen las conversaciones incluidas; los canales son conteos observados, no el denominador de una cuenta. La taxonomía es not-applied: este módulo no reclasifica problemas. Mapping proviene de revisiones seleccionadas; pipeline canonical-source-v2 identifica la proyección de dataset y canales. Fuente sin versión/fecha/canal suficiente se señala; no pasa a evidencia completa por tener filas.

Importes de órdenes vinculadas: aggregateMoney conserva identidad canónica, BigInt, moneda, exponente y desconocidos. No son pérdidas, ahorro ni ingresos recuperados. Cambios de filtros/método/taxonomía/unidad monetaria/cobertura impiden deltas monetarios comparables; los conteos se muestran como descriptivos y savings es null. Una explicación humana no autoriza mezclar métodos distintos: volver a procesar bajo el mismo contrato exige crear un corte nuevo y mantener los anteriores.

Si el canal canónico falta, se usa sólo evidencia raw aceptada enlazada a la revisión actualmente seleccionada: source_revision, content_hash normalizado, canonical_id y connection_id. El snapshot guarda huella y canal, no cuerpo ni credenciales. Zendesk via.channel y HubSpot originalChannelId mantienen prefijo de proveedor; no se asumen equivalencias entre IDs. Datos contradictorios o ausentes permanecen unknown. Fuentes primarias del contrato de canal: [Zendesk Via](https://developer.zendesk.com/documentation/ticketing/reference-guides/via-object-reference/) y [esquema Thread de HubSpot](https://developers.hubspot.com/docs/api-reference/legacy/conversations/conversations/threads/update-conversation). Sólo se consultó documentación pública, no se ejecutó el PATCH de ese ejemplo ni una API autenticada.

Las páginas de50cortes mantienen el timestamp PostgreSQL con sus microsegundos en el cursor: convertirlo a Date perdería registros empatados. El formulario valida fechas de calendario;30-febrero no se normaliza a marzo. Los importes en UI se formatean desde strings y el exponente congelado, sin convertirlos a Number.

Límite de esta operación síncrona:10000filas por tipo (conversaciones, mensajes, órdenes, eventos de alias) en la organización. Por encima falla cerrado; no produce un corte parcial con apariencia completa. Las revisiones ambiguas o alias legacy sin nueva aprobación también impiden congelar una identidad falsa. Este límite y el ensayo de carga a escala real permanecen pendientes de revisión/capacidad enterprise; no presentarlo como escala ilimitada. El proveedor financiero del workspace futuro debe distinguir kind=migration-source-v1 de un snapshot de métricas; estos cortes de dataset no reemplazan componentes financieros.

Se mantienen los archivos de origen, el paquete05 y los primeros paquetes06. La integración conjunta se prueba en otra copia; no modifica la raíz ni los candidatos oficiales. Revisión independiente de05/06 pendiente por cuota de agentes; S01/S02 real y SQL remoto requieren permisos legítimos.
