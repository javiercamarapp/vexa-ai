# Durable CRM page synchronization

`sync.mjs` is server-only. Supply the existing `createDatabase` with an authenticated identity and a dedicated non-superuser PostgreSQL pool; never a browser, service-role or owner client. SQL migration008 is additive and is not remotely applied by this module.

`createSyncRepository({database})` implements ensure, claim, current, commitPage, release and readPayload. `runSync` accepts a connection ID, `mode` live/backfill, a versioned window `{from,to,overlapSeconds,version}`, a worker UUID and an adapter factory. Mapping is explicitly `crm-canonical-v1`. SQL derives the tenant from the active database identity, revalidates membership every transaction and active connection before fetch and commit. Leases use the database clock, a monotonically increasing fence and page-version CAS. An expired worker cannot commit. No token is persisted.

Every accepted page commits canonical F02 revisions, originals, row errors, page history and its opaque provider checkpoint in one SQL transaction. No cursor update precedes these effects. SQL errors roll back the entire page. An uncertain COMMIT acknowledgement is retried by reloading SQL state; no in-memory cursor advances. `maxPages` or deadline returns a durable continuation. A failed fetch throws and leaves the last committed checkpoint. A terminal page is required to mark done. A new live window has a distinct scope/import; the overlap revisits revisions and F02 identity deduplicates them across imports. Opaque revisions are never sorted by timestamps to select a winner.

`createCRMAdapterFactory(config)` wires the reviewed HTTP adapters. Zendesk starts at `fetchFrom=from-overlapSeconds`; its opaque checkpoint continues within that window. HubSpot v3 performs a conservative full scan: the reviewed routes do not yet support a verified incremental update filter. `to` declares the requested observation window; it is not a claim that the provider offers a historical point-in-time snapshot or server-side upper bound. Provider coverage and originals remain available. Full scans can cost more local work but do not invent timestamp-based omission. Separate scopes prevent live/backfill cursors from overwriting each other.

HubSpot threads and Zendesk tickets become conversations. Confirmed linked messages with complete bodies and coherent role/visibility use the existing `persistCanonical`: customer/agent requires public, internal requires internal. Unknown or contradictory visibility stays quarantined; no synthetic customer is inferred. Unknown roles, metadata-only tickets/notes, incomplete bodies and explicit source deletion markers are also durably quarantined. A404 never deletes a canonical record. Deleted source data requires the separate retention workflow. Attachments are not fetched.

Every record envelope and rejection context must match the authorized tenant, connection, source and source account before any page effects persist. Missing or foreign scope rolls back the entire page. Connection identity must also agree with every previous sync scope and canonical revision provenance; changing source/account requires a new connection ID. Starting a new window does not allow mixing old and new account history.

Original raw JSON and normalized bodies are stored in FORCE-RLS `sync_raw_objects`, denied to direct authenticated clients and service_role; backend reads require the selected tenant and active owner/analyst membership. These are actual objects, not hash references without a writer. `readPayload({payloadRef})` resolves canonical import payload references to their original and normalized JSON under current identity; importId/rowRef lookup is also supported. HTML remains inert. Raw/page history has no backend UPDATE/DELETE grants. Retention currently fails closed: removal requires a separately authorized retention migration/workflow; source deletion never silently erases history.

A message preceding its conversation is first retained as `REFERENCE_MISSING`. When an unambiguous parent arrives, the transaction records a distinct `:linked-v1` recovery import row using the original normalized payload. It does not overwrite the original rejection. The original row and successful recovery are separate processing attempts in import accounting; logical canonical identity remains deduplicated. No arbitrary thread is inferred for notes. All eligible missing-reference rows are processed before marking the final page done; no fixed-size backlog is silently abandoned.

Local proposal only. Live S01/S02 evidence, remote SQL authorization, cloud deployment and F03 acceptance remain separate gates. No tests here claim production or real customer access.
