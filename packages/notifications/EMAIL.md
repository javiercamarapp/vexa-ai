# F06-10 — propuesta de correo transaccional

Integración sobre `6c8776dd0e281981f55237e07599efd9891cc815`, posterior al cierre de F06-09. Este documento describe F06-10; su aceptación requiere el gate y la revisión independiente de la composición final.

`email.mjs#createTransports(env)` es el módulo de despliegue que carga el daemon existente usando `VEXA_NOTIFICATION_TRANSPORT_MODULE`. Devuelve `{email}` con `configured`, `resolveRecipient`, `send` y `close`. Sólo identidades activas VEXA de `auth.users` con email confirmado; ninguna lista de destinatarios CRM ni dirección HTTP libre. `prepare` exige outbox email en sending y lease vigente, y vuelve a comprobar emisor, política y su responsable, preferencias, visibilidad del recurso y destinatario activo, confirmado y no bloqueado antes de obtener su dirección. Una revocación conocida o supresión devuelve una negativa normal que bloquea el transporte sin intento; un fallo de almacenamiento conserva incertidumbre. HTML/texto adaptados selectivamente del banco1a0df4e4 y unificados con la presentación Auth de VEXA (verde, blanco y negro); digest genérico, CTA al centro autenticado, sin datos del recurso. Las plantillas individuales permanecen disponibles, pero el daemon agrupa avisos y envía la plantilla digest.

Configuración servidor (nunca NEXT_PUBLIC):
- `VEXA_EMAIL_MODE=resend`, `RESEND_API_KEY`, `VEXA_EMAIL_FROM` (dirección simple) y `VEXA_APP_ORIGIN` (origen HTTPS sin path).
- `VEXA_EMAIL_REPLY_TO`: opcional, dirección simple de un buzón atendido propio. Un valor inválido bloquea el transporte; no se inventa ni se envía una dirección predeterminada.
- `VEXA_EMAIL_DATABASE_URL`: login dedicado con pertenencia sólo al rol NOLOGIN `vexa_email_service`; las funciones SQL usan SET LOCAL ROLE y no permiten acceso directo a tablas. Provisionar credencial propia, nunca reutilizar service_role de Supabase ni contraseña del propietario.
- `VEXA_EMAIL_DATABASE_CA_PEM`: certificado CA opcional para la conexión PostgreSQL dedicada, compartido por worker y webhook. Se reutiliza `databasePoolOptions`; no se admiten parámetros URI que anulen su contrato TLS ni se desactiva la verificación del certificado.
- Local: `VEXA_EMAIL_MODE=mailpit` y `VEXA_MAILPIT_SMTP_PORT`; host fijo127.0.0.1, SMTP sin TLS exclusivamente loopback, sin relay de salida. No requiere key Resend.
- Webhook: `RESEND_WEBHOOK_SECRET` y la misma URL de DB del servicio. POST `/api/webhooks/email`, JSON limitado64KiB. SDK oficial Resend verifica el cuerpo original con Svix; antigüedad máxima300s y replay durable por event_id. No se persiste payload, direcciones ni firmas.

`notification_email_messages` mantiene aceptación y entrega por separado y mapping exclusivo `(provider,provider_id)` a tenant/job/usuario. Mailpit sólo acepta localmente: delivery permanece unknown, y sus IDs nunca se concilian como Resend. Un accepted del proveedor jamás significa delivered. El webhook ignora tenant y destinatarios del payload. Guarda orphans sin modificar ningún job, y los asocia atómicamente cuando el SDK devuelve el ID y se registra la aceptación. Advisory lock por provider ID serializa receipt/mapping. Reducir todos los eventos persistidos impide regresión ante retrasos o fuera de orden; complained/bounced/suppressed/failed prevalecen sobre delivered y delayed/sent. Los eventos opened/clicked no producen read.

Una excepción/timeout después del intento produce uncertain en el consumidor09. Si se pierde el resultado SDK antes de guardar mapping, el orphan se conserva: recuperación operativa debe verificar el ID con el proveedor y llamar al registro de aceptación sobre la clave ya preparada; no se adivina la asociación ni se reenvía automáticamente. La resolución del outbox uncertain sigue el verificador/evidencia de09. SMTP no ofrece idempotencia remota; la recuperación09 no reenvía uncertain. La clave idempotente Resend no es una promesa de exactly-once.

SDKs pinned: Resend6.28.1, Nodemailer10.0.10; pg8.16.3 existente. web-push3.6.7 incluido por ownership compartido con propuesta304, no ejecutado en este scope. Instalación y builds únicamente en copia temporal.

Fuentes consultadas23-sep-2026: https://resend.com/docs/webhooks/verify-webhooks-requests y https://resend.com/docs/api-reference/emails/send-email . Prevalece verificación del body original de documentación oficial sobre el ejemplo JSON.stringify de la habilidad email-best-practices.

No validado por esta propuesta: dominio/remitente real, SPF/DKIM/DMARC, entrega Resend externa, Gmail/Outlook/Apple Mail, producción ni revisión independiente de seguridad. Requieren dominio/cuentas/autorización. No se envió correo externo ni se modificaron controles, gates o Git.

Cancelación: SDK pinned propaga las opciones de `emails.send` al `fetch` estándar; se pasan AbortSignal y redirect:error. Base URL oficial fija; se deshabilita sólo el logger de la instancia SDK, que podría incluir cuerpos del proveedor. Mailpit usa `createMailpitSender({port})`: socket propio por intento con `net.createConnection({signal})`, destruido al terminar; no cierra conexiones de otros intentos. El puerto SMTP inyectado para ensayos debe implementar `sendMail(message,{signal})` con la misma semántica. Si ya hay una respuesta accepted, su mapping se conserva incluso si llega después el aborto; no se convierte una observación real en un reintento.

Repositorio: adquisición acotada5s, liberación de clientes adquiridos tarde, query_timeout6s y statement_timeout5s; rollback con límite y destrucción del cliente si falla. Un pool inyectado debe implementar el contrato pg `query({text,values,query_timeout})` y `release(destroy)`.

Marca compartida: `apps/web/src/lib/brand.mjs` y `brand.json` definen el asset público tanto para la web como para correo. `logoPath:null` conserva el nombre provisional; al proporcionar el logo, configurar un PNG/JPEG bajo `/brand/` del mismo origen HTTPS. El build del consumidor incluye ambos archivos. Cabecera y CTA centrados, contenedor máximo560px, alternativa texto y atributos `lang="es" dir="ltr"` también en los hijos directos del body. Los previews de navegador no acreditan compatibilidad específica de Gmail/Outlook/Apple Mail.

Supresión durable: una queja, un rebote identificado expresamente como permanente o un aviso `email.suppressed` bloquean nuevos envíos del mismo tenant, usuario y hash del buzón normalizado. Un rebote genérico o temporal no se interpreta como permanente. `delivered`, otro opt-in o un replay no rehabilitan el buzón; cambiar a una nueva dirección Auth confirmada con preferencias activas permite preparar para esa dirección, conservando la supresión anterior. No hay una interfaz para rehabilitar automáticamente el mismo buzón. Los recibos huérfanos no afectan a usuarios hasta que el mapping interno asocia el ID del proveedor; el payload externo no selecciona tenant ni destinatario.
