# Consumidor de notificaciones · F06-09

Propuesta local: catálogo y emisores de negocio siguen desconectados. No incluye transportes Resend/web-push ni suscripciones o webhooks. No hay endpoint público para elegir destinatarios, emitir o conciliar. Las interfaces son internas de servidor.

`createOutboxRepository({database,leaseMs,verifyReconciliation?})` reutiliza createDatabase. Owner configura políticas versionadas con CAS y encola referencias. `enqueueIn(scope,input)` permite insertar evento, job y outbox en la misma transacción import del negocio; cualquier error revierte todos. Los destinatarios son UUID de memberships activas de VEXA, nunca contactos CRM. Invited no se encola.

Se usan public.jobs y public.attempts como única autoridad de lease y fence. La metadata de entrega está en notification_outbox; sus items agrupan eventos de un mismo tenant/usuario/canal y versión de política durante una ventana opcional, hasta100 por digest. No entran eventos nuevos después del claim. Cada referencia se reautoriza antes de enviar; las retiradas se suprimen. El mensaje es genérico, sin cifras ni texto de CRM, y enlaza al centro autorizado.

La cuota persistida por tenant/usuario/canal se reserva antes del efecto y no se devuelve ante timeout o incertidumbre. Política exige intervalo1s..24h (valor operativo recomendado60s), digest0..1h,1..10 intentos y vida1s..30d; defaults del ejemplo de configuración deben enviarse explícitamente. Configuración ausente/deshabilitada, permisos/preferencias ausentes, resolver inválido o errores impiden efectos.

`consumeNotification` adapta el consumeOne existente: heartbeat durante operaciones acotadas, renew antes del efecto/commit, beginSend persistido y finish con fence vigente. Claimed vencido puede retomarse; sending vencido pasa a uncertain, aunque haya expirado su vida. Accepted significa aceptación de transporte o persistencia in-app, nunca delivered/read. Fallo desconocido después de comenzar es uncertain. Sólo un rechazo conocido como retry programa backoff desde1s exponencial hasta1h, respetando Retry-After máximo24h y deadline/intentos; agotamiento es dead.

Alarmas blocked/uncertain/dead se conservan en dead_letters y health() las expone sin generar notificaciones recursivas. No se borra historia ni se ocultan errores como colas vacías. La conciliación requiere owner vigente, fence esperado, clave idempotente y evidencia vinculada verificada por un puerto de servidor. El alcance y permisos se revisan otra vez. Accepted no inventa entrega; not_sent permite un retry explícito, nunca una liberación automática por TTL. SQL exige un receipt inmutable de notification_reconciliation_evidence con tenant/job/fence/decisión/idempotencyKey/providerId coincidentes. El rol privado vexa_notification_verifier sólo registra y lee sus receipts; no se concede a backend, usuarios, servicio ni roles de negocio. createReconciliationVerifier({pool,verify}) usa una conexión dedicada a ese rol y una comprobación independiente de evidencia del proveedor. No basta una UUID o un booleano del solicitante. Una caída tras guardar la prueba permite reutilizar el receipt idéntico; nunca lo convierte por sí solo en conciliación. El callback de verificación está acotado a10s y falla cerrado.

## Ejecución

`node packages/jobs/durable/build.mjs OUT` exige OUT fuera del repositorio y genera runtime, notifications y platform compilada. El proceso requiere pg resuelto desde la instalación `npm ci` con el lock del repositorio; no descargar dependencias en el candidato. Ejecutar `node OUT/packages/notifications/daemon.mjs --once`.

Se usan las variables Auth/database/worker del consumidor existente. Elegir VEXA_WORKER_DISPATCHER=enabled para rotación durable o VEXA_WORKER_TENANT fijo. VEXA_NOTIFICATION_TRANSPORT_MODULE es opcional y debe ser un archivo .mjs absoluto privado que exporte createTransports(env); no se importa desde URLs ni desde peticiones cliente. Los adaptadores configurados implementan configured(), resolveRecipient() y send(). Sin módulo, in-app funciona si la política/preferencia/recurso lo permiten y email/push quedan blocked. Las implementaciones de proveedor pertenecen a F06-10/11.

VEXA_NOTIFICATION_TIMEOUT_MS es1..10000 (default10000), VEXA_NOTIFICATION_POLL_MS100..60000(default1000). Cada ciclo crea/cierra runtime y rota scope. SIGTERM/SIGINT no toman otro claim mientras termina el efecto acotado. El hook afterSend es de servidor y permite observar/crashear después del efecto y antes del commit en ensayos; no es un failpoint HTTP. Transportes y snapshots se copian para impedir que objetos mutables redirijan un destinatario validado.

Pruebas locales usan Auth/PG y HTTP loopback sintéticos. No acreditan proveedores ni permisos/configuración de producción. Las funciones internas con SET de claims restauran su configuración automáticamente; no se conceden al backend helpers de impersonación arbitraria.
