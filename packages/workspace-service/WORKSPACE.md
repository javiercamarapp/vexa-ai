# Overview y Problems: una publicación y un alcance

La fuente financiera es una publicación canónica de F05. Este adaptador no publica ni modifica dinero. `GET /api/workspace` admite `resource=metrics|problems`; ambas vistas comparten fechas UTC semiabiertas, moneda, base de importe, snapshot y filtros de SKU/origen. La fecha es la fecha efectiva del registro económico (`occurred_at`), no una fecha de pedido inferida. Otras bases se rechazan.

`base_snapshot_id` y `base_scope_hash` identifican la publicación F05. `scope_hash` identifica la vista derivada, incluyendo filtros y versiones exactas de asociaciones. `cursor_auth_hash` añade usuario, tenant, rol y versión de permisos; no es un hash de datos. Cambiar página no cambia la normalización ni suma filas por problema. Los importes son cadenas enteras exactas; desconocido y subtotal conocido permanecen separados.

Un propietario puede declarar SKU y origen en `/economics`, mediante `POST /api/workspace/mappings`. Debe seleccionar una fila real, aportar evidencia operacional y confirmar. Cada escritura exige `expectedVersion`; deshacer añade una revisión con `active:false`. Una asociación se refiere a la fila física y revisión del ledger, nunca a un UUID legado coincidente. La identidad de origen es declarada por el propietario. SKU significa **órdenes que contienen SKU**, no ventas por línea.

Al abrir una vista sin `scope_hash`, el servidor puede materializar un manifiesto inmutable de referencias. Es una caché de alcance, no aprobación humana ni publicación financiera. La acción DB `materialize` tiene los roles lectores y una política específica para insertar ese manifiesto; la lectura financiera normal sigue siendo una transacción de sólo lectura. Secuencia: lectura autorizada, inserción validada de referencias, nueva lectura autorizada. La última fase impide devolver datos retirados entre operaciones.

Una URL con snapshot y scope hash fija las versiones exactas. Una asociación posterior crea otro hash al solicitar una vista nueva; no cambia la exportación anterior. La lectura valida nuevamente actores, evidencia y fuentes; una revocación puede hacer inaccesible la vista antigua, pero no sustituye sus datos por datos actuales. Si falta una asociación de SKU/origen, se conserva pertenencia desconocida y cobertura parcial. No se rescata una asociación anterior cuando el último autor pierde autorización.

La proyección lee exclusivamente las filas enumeradas en `input_manifest` del snapshot. Reutiliza el adaptador económico para unión de órdenes, aliases y reembolsos/reversals. Las filas P1/P2 no son aditivas. Los metadatos históricos de problemas se verifican contra la fecha del corte y los runs capturados; si la evidencia deja de ser accesible, la consulta falla cerrada. Un merge administrativo conserva los IDs, etiquetas y cifras históricos; `stale` sólo advierte que la versión actual cambió, sin reescribir la publicación. La alerta de seguridad es una señal **actual** autorizada separada de las cifras históricas y no depende del importe o del filtro.

`GET /api/workspace/export` requiere snapshot y scope hash, conserva el mismo alcance y exporta todas sus filas. JSON devuelve el bundle; CSV incluye IDs, hashes, familia y minor units exactos, sin texto editable ni fórmulas. La exportación F05 sin filtros no se usa para exportar una vista filtrada.

Sin publicación: `empty`. Cobertura parcial: `partial`. Versión actual posterior: `stale`; evidencia histórica no autorizada o no verificable: error. Fallos de infraestructura/autorización son errores HTTP, nunca ausencia fabricada. La ausencia de configuración tiene un contrato 503 explícito; no cubre fallos operativos. Clientes, recomendaciones, intervenciones, briefs, detalle de problemas y otros proveedores de F06 siguen fuera del alcance de esta entrega F06-01.
